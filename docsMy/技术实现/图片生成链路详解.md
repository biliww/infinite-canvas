# 图片生成链路详解

> 本文聚焦于 infinite-canvas 项目中**图片生成（文生图）**这条核心链路，逐层拆解每个环节的代码实现与职责边界。

---

## 一、链路全景

```
用户输入 prompt，点击生成
        ↓
[前端触发层]  canvas-node-prompt-panel.tsx
        ↓  onGenerate(nodeId, "image", prompt)
[前端调度层]  canvas-client-page.tsx → handleGenerateNode()
        ↓  收集上下文 → 调用 API
[前端 API 层] services/api/image.ts → requestGeneration()
        ↓  POST /api/v1/images/generations
[代理层]      Next.js API Route（透明转发）
        ↓  fetch http://127.0.0.1:8080/api/v1/images/generations
[路由层]      Go Gin → handler.AIImagesGenerations
        ↓
[处理层]      handler/ai.go → proxyAIRequest()
        ↓  JWT 鉴权 → 查积分 → 选渠道 → 预扣费 → 转发
[上游 AI]     OpenAI 兼容接口返回 b64_json
        ↓
[前端存储]    IndexedDB（localforage）→ 更新节点状态
```

---

## 二、第一层：用户触发

**文件**：`web/src/app/(user)/canvas/components/canvas-node-prompt-panel.tsx`

用户在画布节点上的输入框中写下 prompt，按 Enter 或点击发送按钮触发生成。

```typescript
const submit = () => {
    const text = prompt.trim();
    if (!text || isRunning) return;

    // 将生成请求抛给父组件（canvas-client-page）处理
    onGenerate(node.id, mode, text);
    setPrompt("");
};
```

**关键点：**
- `mode` 由节点类型决定，图片节点传入 `"image"`
- `isRunning` 防止重复提交
- 组件本身不做任何 API 调用，职责单一，只负责 UI 交互

---

## 三、第二层：调度与上下文构建

**文件**：`web/src/app/(user)/canvas/[id]/canvas-client-page.tsx`

这是整条链路的**核心调度层**，接收触发后执行以下动作：

### 3.1 收集上游节点的参考图/文本

```typescript
const context = await hydrateNodeGenerationContext(
    buildNodeGenerationContext(nodeId, nodes, connections, prompt)
);
```

`buildNodeGenerationContext` 会沿着画布连线向上游遍历，收集所有连接节点的内容（图片或文本），构建成生成上下文。`hydrateNodeGenerationContext` 负责把存储在 IndexedDB 中的 `storageKey` 转换为实际的 `dataUrl`，供后续接口使用。

### 3.2 判断走文生图还是图生图

```typescript
const hasRefImages = context.referenceImages.length > 0;

if (hasRefImages) {
    // 有参考图 → 图生图
    result = await requestEdit(config, effectivePrompt, context.referenceImages, imageSettings);
} else {
    // 无参考图 → 文生图
    result = await requestGeneration(config, effectivePrompt, imageSettings);
}
```

**这是文生图和图生图的分叉点**：上游节点有图片连接时走 `/images/edits`，否则走 `/images/generations`。

### 3.3 创建占位节点（乐观 UI 更新）

在 API 请求发出之前，先在画布上插入一个 `status: loading` 的占位节点，让用户立刻看到"正在生成"的反馈，而不是等待接口返回后再渲染。

## 四、第三层：前端 API 封装

**文件**：`web/src/services/api/image.ts`

```typescript
export async function requestGeneration(config: AiConfig, prompt: string, settings: ImageSettings) {
    const response = await axios.post(
        aiApiUrl(config, "/images/generations"),  // 根据 channelMode 决定 URL
        {
            model:           config.model,
            prompt:          withSystemPrompt(config, prompt),
            n:               settings.n ?? 1,
            quality:         settings.quality ?? "medium",
            size:            settings.size ?? "1024x1024",
            response_format: "b64_json",   // 返回 base64，避免图片 URL 过期
        }
    );
    return response.data;
}
```

**`aiApiUrl` 的渠道路由逻辑：**

```typescript
// web/src/stores/use-config-store.ts
function aiApiUrl(config: AiConfig, path: string) {
    if (config.channelMode === "remote") {
        return `/api/v1${path}`;           // 走后端代理（默认，需要登录）
    }
    return buildApiUrl(config.baseUrl, path);  // 直连 AI 服务（本地模式）
}
```

`response_format: "b64_json"` 是一个重要设计决策：返回 base64 而非 URL，可以避免 OpenAI 图片 URL 一小时后过期的问题，图片数据完全由前端自行管理。

## 五、第四层：Next.js 代理转发

**文件**：`web/src/app/api/[...path]/route.ts`

```typescript
const apiBaseUrl = process.env.API_BASE_URL || "http://127.0.0.1:8080";

export async function POST(request: NextRequest, { params }: { params: { path: string[] } }) {
    const path = params.path;
    const target = `${apiBaseUrl}/api/${path.join("/")}${request.nextUrl.search}`;

    const response = await fetch(target, {
        method:  "POST",
        headers: request.headers,
        body:    request.body,
    });

    return new Response(response.body, {
        status:  response.status,
        headers: response.headers,
    });
}

export const maxDuration = 300;  // 5 分钟超时
```

这一层是纯粹的**透明代理**，不做任何业务逻辑，只解决跨域和统一出口的问题。所有请求头（包括 JWT Token）原样透传到 Go 后端。

---

## 六、第五层：Go 路由与鉴权

**文件**：`router/router.go`

```go
v1 := api.Group("/api/v1", middleware.UserAuth)  // 所有路由需要 JWT 鉴权
v1.POST("/images/generations", handler.AIImagesGenerations)
```

**文件**：`middleware/auth.go`（UserAuth 中间件）

中间件从请求头取出 JWT Token，解析出用户 ID，将用户对象注入到 `request.Context()` 中，供后续 Handler 使用。鉴权失败直接返回 401，不进入 Handler。

---

## 七、第六层：核心处理——积分 + 渠道 + 转发

**文件**：`handler/ai.go`

这是后端最关键的一层，`proxyAIRequest` 实现了三件核心事：

### 7.1 解析模型名称

```go
body, contentType, modelName, err := readAIRequest(r)
// 从请求 JSON 中提取 "model" 字段
// 支持 JSON body 和 multipart/form-data 两种格式
```

### 7.2 积分预扣

```go
user, _ := service.UserFromContext(r.Context())   // 从 JWT 上下文取用户
credits, _ := service.ModelCost(modelName)         // 查该模型单次消耗积分

// 预扣积分（请求成功后正式扣，失败自动退还）
service.ConsumeUserCredits(user.ID, modelName, credits, path)
```

积分单价在后台管理界面配置，存储在 `settings` 表的 `ModelCosts` 字段中，图片生成按 `n`（生成张数）乘以单价计费。

### 7.3 加权随机渠道选择

```go
channel, err := service.SelectModelChannel(modelName)
```

```go
// service/settings.go
func SelectModelChannel(modelName string) (model.ModelChannel, error) {
    // 筛选出：已启用 + 支持该模型 + 配置了 BaseURL + APIKey 的渠道
    channels := modelChannelsForModel(settings.Private.Channels, modelName)

    // 按 weight 字段加权随机（支持多渠道负载均衡）
    // weight=3 的渠道被选中概率是 weight=1 渠道的 3 倍
    return weightedRandom(channels)
}
```

这个机制允许管理员配置多个上游 AI 服务（如多个 OpenAI 账号、不同区域的接口），通过权重控制流量分配，也可在某个渠道异常时快速下线。

### 7.4 转发请求到上游 AI

```go
// 构建上游 URL（自动补充 /v1 前缀）
upstreamURL := service.BuildModelChannelURL(channel, "/images/generations")
// 例：https://api.openai.com/v1/images/generations

req, _ := http.NewRequest("POST", upstreamURL, body)
req.Header.Set("Content-Type", contentType)
req.Header.Set("Authorization", "Bearer "+channel.APIKey)  // 用渠道密钥，不暴露给前端

// 透传响应（含失败时自动退还积分的回调）
copyAIResponse(w, req, func() {
    service.RefundUserCredits(user.ID, credits)
})
```

**安全要点**：前端用户完全不知道上游 AI 的 `APIKey` 和 `BaseURL`，所有密钥只在 Go 后端内存中，通过管理接口写入数据库。

## 八、第七层：上游 AI 返回与前端存储

上游 AI 服务返回：

```json
{
    "created": 1716000000,
    "data": [
        { "b64_json": "iVBORw0KGgo..." }
    ]
}
```

前端 `canvas-client-page.tsx` 接收到 base64 数据后：

```typescript
// 1. 转为 dataUrl
const dataUrl = `data:image/png;base64,${result.data[0].b64_json}`;

// 2. 存入 IndexedDB（避免 localStorage 大小限制）
const storageKey = await uploadImage(dataUrl);

// 3. 更新节点元数据
updateNode(nodeId, {
    status:     "success",
    storageKey: storageKey,  // 节点只存引用 key，不存原始数据
    content:    dataUrl,     // 内存中保留 dataUrl 供渲染
});

// 4. 持久化画布状态到 localStorage
saveCanvasState();
```

**存储分层设计：**

| 数据 | 存储位置 | 原因 |
|---|---|---|
| 图片二进制 | IndexedDB（localforage） | localStorage 只有 5MB，图片太大 |
| 节点元数据（storageKey 等） | localStorage | 轻量，读写快 |
| 渠道密钥、积分 | 数据库（SQLite/MySQL） | 需要服务端持久化 |

---

## 九、异常处理机制

| 环节 | 异常处理 |
|---|---|
| 前端提交 | `isRunning` 标志防止重复提交 |
| 用户积分不足 | Go 后端校验，返回 402，前端弹出提示 |
| 渠道不可用 | 加权随机失败时返回 503 |
| 上游 AI 报错 | `copyAIResponse` 检测非 2xx，触发积分退还回调 |
| 图片生成超时 | Next.js 代理层 `maxDuration: 300`（5 分钟） |
| 节点占位 | 失败后将占位节点状态改为 `error`，显示重试按钮 |

---

## 十、小结

图片生成链路涉及 **7 个层次、5 个文件**，每层职责清晰：

| 层次 | 文件 | 职责 |
|---|---|---|
| 触发层 | `canvas-node-prompt-panel.tsx` | UI 交互，收集 prompt |
| 调度层 | `canvas-client-page.tsx` | 上下文构建，文生图/图生图分叉 |
| API 层 | `services/api/image.ts` | 封装 HTTP 请求参数 |
| 代理层 | `app/api/[...path]/route.ts` | Next.js 透明转发 |
| 路由层 | `router/router.go` + 中间件 | JWT 鉴权，分发到 Handler |
| 处理层 | `handler/ai.go` | 积分扣费 + 渠道选择 + 请求转发 |
| 存储层 | localforage + localStorage | 图片 IndexedDB，节点状态 localStorage |
